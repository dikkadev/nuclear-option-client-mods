# NuclearLiveFeed viewer

A static web page that connects to the NuclearLiveFeed mod and draws the live feed over the Nuclear Option map. Vite and TypeScript, no framework. The map itself is drawn by the separate `nuclear-option-map` library; map data is loaded from `/map-data/` and never copied into this app.

## Develop

Requirements: the map library built in the sibling `nuclear-option-map` checkout (`dist/browser/index.js`, override with `NOM_LIBRARY`).

```bash
pnpm install
pnpm dev            # http://127.0.0.1:5173
```

The Mission picture is at `/mission.html` there (the map's toolbar button always opens the public site). The dev server proxies `/map-data/` and `/maps/` to the public site (`NOM_MAP_ORIGIN`, default `https://map.scramd.com`), which serves `manifest.json`, `variants.json`, the satellite, topographic and game views. Set `NOM_MAP_DATA` to a local folder (for example the library's extracted `maps/`) to work without the site; then only the game view exists. The feed comes from the game with the mod installed.

URL parameters: `?feed=ws://host:port` (also editable by clicking the status; remembered locally) and `?data=URL` for another map-data base. Without map data, the page draws the game grid on a blank map. The page reads feed protocol `PROTOCOL` (in `src/feed.ts`); when the mod's hello names another version, it stops and shows "Update mod" or "Reload page".

## Guide page

`guide.html` (`src/guide.ts`, `src/guide.css`) is the player guide at `/guide` (the dev server serves it there too), the only place that explains the map: a quick start, a numbered picture of the whole screen, what the map shows, an annotated contact and symbol legend with the full unit list, every line and mark, the screen parts, target picking, the layers panel, keys, connection states, mod settings, exact values ("Numbers at a glance") and problems. A page finder (contents and top; `/` focuses it) searches terms, explanations and the unit list. Every number in it comes from the viewer and mod code; when one changes, change the guide too. Its pictures of the map are screenshots of this page with an example battle; `scripts/guide-pictures/` retakes them. It is written for players: no feature status or development notes. Opening the site still goes straight to the map; the map links to the guide from the waiting box (same tab) and the toolbar (new tab, so a running map keeps its state). The guide shows the connection status through its own feed connection, which reads only the text messages, and draws its symbols with the map's own `symbols.ts`, so the legend matches the map. When a map feature changes, update the guide in the same change.

## Display

- Base map: Satellite (default), Topo or Game. Effects (Dim, Muted, Night) apply to the whole map, only land or only water; the land/water mask comes from the topography tiles' alpha channel.
- Units are drawn through an icon-set layer (`src/symbols.ts`): every caller describes a unit as an `IconSpec` (role, side, status, group frame, optional fill color, muted) and the active `IconSet` draws it, on the map, in the details panel, in the Mission picture and in the guide's legend. Two sets, chosen in Layers → Map → Icons (`nlf.view.icons`, default NATO) and separately in the Mission picture: NATO (`src/icon-sets/nato.ts`), APP-6(D) symbols drawn by `milsymbol` (MIT); and Game (`src/icon-sets/game.ts`), the game's own icons. Game draws aircraft with the type's map silhouette turned to the heading, and ground units, ships, buildings, supplies and pilots with the type's target icon (rectangle frame for own and neutral, diamond for enemy, kind glyph inside), filled with the side color with the game's lines dark on top; airbases stay NATO. A set implements `draw`, `drawGroup`, `canvas` and `markup` and is listed in `ICON_SETS`.
- Game icon data is game-derived. `uv run --script scripts/game-icons.py "<game>/NuclearOption_Data"` builds it from a local client into the Git-ignored `src/icon-sets/generated/game-icons.json` (white alpha masks per sprite, plus each unit type's map and friendly/hostile icon). The build bundles it as a lazily loaded script chunk, the only way it reaches map.scramd.com (user decision 2026-11-08: hosting inside the built page is fine, never in the repository). A build without the file offers NATO only. Rebuild it after a game update that changes unit icons. Roles come from the game catalog in `src/symbology/`, taken over from the retired nomap app; this copy is now the only one. Last-known enemy tracks use the anticipated (dashed) status; damaged and destroyed units show the standard condition bar.
- Labels appear for hovered and selected units and player callsigns; the Labels option shows all. Nearby ground units and ships of one side group into a frame with a count (option Group).
- Show filter (`src/filters.ts`, Layers → Show): each side and each unit category (from the role; supplies and pilots are always Buildings and supplies, buildings are Air defense, Radar or Buildings and supplies) is Show, Dim or Hide; a unit takes the stronger choice. Dim draws a muted icon (gray, half opacity), no label unless hovered, no path, trail or new-contact pulse, a thin gray air-defense edge; it stays clickable, sorts to the bottom of Contacts and is left out of Shift-drag target boxes. Hide drops the unit from the map, Contacts and its area. Never filtered: own aircraft, selection, targets, missiles guiding on you. Flight-strip warnings ignore the filter. Default: everything shown except Buildings and supplies (the old Structures switch, migrated once from `structures` in `nlf.view`).

Keys: F fit, Esc clear selection. Click a unit for details.

## Mission picture

**Embed mode** (`?embed=1`, 2026-11-10, for the Wargen panel of the user's server admin): another page shows the Mission picture in a *visible* frame (browsers pause animation frames in hidden cross-origin frames), the page posts `{type:'mission-picture:ready', v:1}` to its parent, takes `{type:'mission-picture:render', v:1, id, mission: <JSON text>, side?, title?}` and answers the sender with `{type:'mission-picture:result', v:1, id, jpeg: Blob}` or `{type:'mission-picture:error', v:1, id, message}`. Only the picture shows, settings are the defaults, nothing is saved, and the mission never leaves the browser. It accepts any origin because it only draws and answers the sender. Tested 2026-11-10 in headless Edge from another origin: ready in about 1 s, a Broken Line war drawn in about 3 s (505 KB JPEG).

Its own page since 2026-11-08 (user request): `mission.html` (`src/mission-page.ts`, `src/mission-image.ts`, `src/mission.css`), public at `https://mission.scramd.com`; the map's toolbar button links there in a new tab, and its help is on that page (the guide keeps a short section with the link). It reads a mission file (open, drop on the page or paste; it never leaves the browser) and draws it in the map's look: the same map library on a hidden canvas with a fixed `pixelRatio`, the same symbols, ground/ship and aircraft grouping and label style. It needs no feed. Its settings start from the live map's defaults and are saved in that origin's `nlf.missionPicture` (the Show filter only once changed); the map's Layers choices do not carry over, because the two sites are separate origins. Settings: point of view, one side (friendly frames) or "Both sides (versus)" (every faction friendly-framed in its own color; the default when more than one faction is joinable), colors Blue and red or Game spectator (the game's exact faction colors, Boscali `#a76bff`, Primeva `#ffb800`, read from the Faction assets on 2026-11-08) with Swap, air defense areas for the other side, all sides or none, base map, tint and its target, groups, labels, symbol and text size, and its own Show filter (without Missiles and bombs). The live map keeps its blue and red. It adds a large title and saves a JPEG below 1,000,000 bytes (lower quality steps until it fits), because the game's Workshop upload refuses previews over 1 MiB. It repaints while tiles load. A mission file has no runway geometry or weapon ranges, so two tables taken from the game files (2026-11-08) supply what the mod sends at run time: `src/runways.ts` (every airbase of both maps with its runways; bases the mission does not list are neutral) and `src/air-defense.ts` (each unit type's anti-air range and ceilings, by the mod's `AirEnvelope` rule). Air defense units then get the live map's merged zones in their side's color, and runways get approach lines on bases that are not hostile. Rebuild both tables after a game update that changes airbases or weapons.

## Build

```bash
pnpm build          # typecheck, then dist/
```

The build bundles the map library.

## Hosting

Public at `https://map.scramd.com` (user decisions 2026-10-29 and 2026-11-01) and `https://mission.scramd.com` (the Mission picture, 2026-11-08). One Cloudflare R2 bucket, `nuclear-live-map-data`, serves both through two custom domains; no Pages project and no Workers run per request. Both hosts share `assets/*` and the map data.

- Bucket keys: the pages (`index.html`, `guide` holding the built `guide.html`, so its address has no extension, `mission` holding the built `mission.html`, `assets/*`), the map catalogs (`manifest.json`, `variants.json`) and the tiles under `tiles/builtin/`, `terrain/` and `candidate-v8/`, mirroring the old map server's `/maps/` paths. Satellite is Satellite V3 from the private backup bucket `nuclear-option-map-backups/satellite-v3/`; the public bucket has levels 0-9, and its `variants.json` lists only those.
- Zone rules on `scramd.com` (managed in Cloudflare, not in this repository): URL rewrites (`/` to `/index.html`; `/map-data/*` and `/maps/*` to the bucket root), a WAF rule that blocks everything except GET/HEAD for the pages (`/`, `/index.html`, `/guide`), `/assets/*.js`, `/assets/*.css` and known tile shapes, a rate limit of 1,000 requests per 10 s per address, cache rules (tiles and assets for a year, page and catalogs by their stored Cache-Control, query strings ignored) and Smart Tiered Cache. No cache rule covers `/guide` yet, so Cloudflare fetches it from the bucket on every request. A new page needs its path in the WAF rule. Host `mission.scramd.com` has the same kind of rules, set up from the user's PC on 2026-11-08: `/` rewrites to the key `mission`, the same map-data rewrites, and its own WAF rule that allows only `/`, the assets and the map data, so neither host serves the other's pages.
- Cache-Control is stored on each object: `index.html`, `guide`, `mission`, `manifest.json` and `variants.json` 5 minutes, everything else a year.

Deploy a page update with `pnpm run deploy:site` (build, upload all three pages, purge the cached pages of both hosts). Build first with the game icon data in place (`scripts/game-icons.py`, see Display), or the deployed page loses the Game icons. It needs `CLOUDFLARE_API_TOKEN` or a `cf auth login` session. Without bash, or with a token limited to the bucket, run `pnpm build` and then `uv run --script scripts/deploy.py` with `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` set; it uploads through R2's S3 API, which accepts such a token. The agent's token for this is the Proton Pass item "Cloudflare - map.scramd.com deploy" (Agent vault): R2 object write on the bucket, cache purge, WAF edit and zone read on scramd.com. Old hashed assets stay in the bucket; they are small and harmless. Changing tiles or catalogs is a separate data task: keep immutable tile paths unchanged or use a new prefix, and purge the cache after replacing a catalog, on both hosts (each caches its own copy).

The map must keep this one HTTPS origin, because Chrome's local network permission is granted per origin, and the mod's Allowed Origins includes it. The Mission picture never connects to the mod, so its origin is not in that list.

The page always shows that it is an unofficial project not affiliated with Shockfront Studios; the full game-content disclaimer opens from that notice.
